# Feature: Add "New Task" button to each board column so users can create tasks from the board

**GitHub Issue:** [#78](https://github.com/Gulybi/KanbAI-Web/issues/78)
**Milestone:** _none_ (unassigned)
**Labels:** `bug`
**Repository:** Gulybi/KanbAI-Web
**Severity:** Major — the board is read-only for task creation; a freshly-populated board (post-[#77](https://github.com/Gulybi/KanbAI-Web/issues/77)) has no in-app way to get its first task, breaking the core Kanban loop end-to-end.

---

## Business Value

### Who is this for?
- **Authenticated KanbAI users** who land on a project board that has one or more columns (either the starter set shipped with [#70](https://github.com/Gulybi/KanbAI-Web/issues/70) or columns subsequently added via [#77](https://github.com/Gulybi/KanbAI-Web/issues/77)) and need to add their first — or Nth — task. Today these users see columns rendered correctly but no control anywhere on the page that creates a task. The only way a task currently appears in the UI is by dragging it from another column; without an existing task to drag, the board is inert.
- **Users on a newly-created project** (the [#70](https://github.com/Gulybi/KanbAI-Web/issues/70) + [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) happy path). Their board is set up with three columns, each empty, each showing only a `"Drop a task here."` hint. They have zero tasks and zero way to produce one — the core Kanban loop is gated behind a missing UI affordance.
- **Team leads populating a board** with the initial backlog of work. Today they must fall back on the backend API directly (out-of-band) to seed any tasks, or accept an empty board; neither is acceptable for an internal demo or end-user onboarding.
- **Keyboard- and screen-reader-only users** who cannot use drag-and-drop even when tasks already exist. Without a create-task affordance they cannot initiate new work; with one, they gain a fully accessible alternative path to contributing to the board.

### Why is it valuable?
Issues [#70](https://github.com/Gulybi/KanbAI-Web/issues/70) and [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) together guarantee a board always has at least one column available. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) is the direct completion of that setup story: it turns each column from a passive drop target into an active authoring surface. Without [#78](https://github.com/Gulybi/KanbAI-Web/issues/78):

1. **The primary product promise fails.** A Kanban tool whose core value is "capture and move work through states" cannot capture work from the UI. The moment a user tries to add their first task they discover the app is read-only for creation, which is the worst possible first impression for an early-stage product.
2. **The columns shipped by [#70](https://github.com/Gulybi/KanbAI-Web/issues/70) / [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) have no payload.** Columns are empty boxes. The user-visible feature that demonstrates the app works end-to-end (create column → create task in column → drag task to next column) has its middle step missing.
3. **The drag-and-drop flow from [#47](https://github.com/Gulybi/KanbAI-Web/issues/47) has no source material.** `PUT /api/task/{taskId}/move` (the move endpoint [#47](https://github.com/Gulybi/KanbAI-Web/issues/47) integrates with) can only move tasks that already exist. With no create-task UI the optimistic-move reconciliation, the rollback-on-reject animation, and the SignalR `TaskMoved` handling — all already shipped — are exercised by *nothing* from a new user's perspective.
4. **The task-detail drawer from [#49](https://github.com/Gulybi/KanbAI-Web/issues/49) + attachment uploads from [#50](https://github.com/Gulybi/KanbAI-Web/issues/50) / [#51](https://github.com/Gulybi/KanbAI-Web/issues/51) / [#55](https://github.com/Gulybi/KanbAI-Web/issues/55) are permanently gated.** The detail drawer only opens for existing tasks ([`board-page.component.ts:249-251` → `handleTaskOpened`](../../KanbAI-Web/src/app/features/board/board-page/board-page.component.ts#L249-L251)), so every feature shipped in milestones #5 and #6 that operates on a task is invisible until [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) provides a way to produce one.
5. **SignalR `TaskCreated` reconciliation is dormant.** [`BoardStateService.onTaskCreated`](../../KanbAI-Web/src/app/features/board/state/board-state.service.ts#L215-L242) already handles the realtime echo (dedupe-by-id, column-guard, sort by `taskOrder`) but is never triggered by the client's own actions — only by out-of-band backend pokes. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) is the first in-app path that exercises this handler.

Fixing [#78](https://github.com/Gulybi/KanbAI-Web/issues/78):
- **Completes the board-authoring story.** After [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) (columns) and [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) (tasks), a user who has just signed up can create a project, accept defaults, and produce a working Kanban flow entirely through the UI — no backend tooling, no workaround.
- **Mirrors the column-create pattern established by [#77](https://github.com/Gulybi/KanbAI-Web/issues/77).** The "empty-column state + trailing affordance + inline create form + optimistic insert + SignalR echo dedupe" pattern is already proven on columns. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) applies the same shape one scope-level down (per-column instead of per-board) so the codebase gains a second worked example of the pattern, ready to be extracted/generalised later if the team ships similar flows (e.g. inline task-rename, subtask creation).
- **Unblocks every downstream task operation.** Because [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) is the first user-authored path that produces a `TaskResponseDto`, it is the gateway to all future in-board task-edit, task-assign, task-delete tickets — each of which needs a task to exist before it can be exercised.
- **Establishes keyboard-first parity with drag-and-drop.** The issue body explicitly requires the flow to work without drag-and-drop; this is the first operation on a task that is fully keyboard-authored end to end.

### What problem does it solve?
Concretely, today:
1. **No create-task affordance exists anywhere on the board.** [`board-column.component.html`](../../KanbAI-Web/src/app/features/board/components/board-column/board-column.component.html) renders a header (name + count), an optional color accent, and either a list of task cards or an empty-zone with the text `"Drop a task here."` — **no button, no input, no menu, no keyboard shortcut**. [`board-page.component.html`](../../KanbAI-Web/src/app/features/board/board-page/board-page.component.html) adds the column strip's trailing "+ Add column" slot (from [#77](https://github.com/Gulybi/KanbAI-Web/issues/77)) and the task-detail drawer (from [#49](https://github.com/Gulybi/KanbAI-Web/issues/49)) but no per-column create-task affordance.
2. **Empty columns are dead ends.** The literal `"Drop a task here."` hint at [`board-column.component.html:23-26`](../../KanbAI-Web/src/app/features/board/components/board-column/board-column.component.html#L23-L26) tells the user their options are (a) drag a task here, but there are no tasks to drag. The empty-state has no "Add your first task" call-to-action; it is a message that demands an action the user cannot perform.
3. **`TasksApiService` has no `createTask` method.** [`tasks-api.service.ts:15`](../../KanbAI-Web/src/app/features/board/services/tasks-api.service.ts#L15) declares `TaskMoveOperation = 'move'` as the only supported operation — explicitly "Only task operation supported in this ticket is a drag-triggered move." The service has no method that posts to `POST /api/task/column/{columnId}` (the documented backend endpoint — see [`.claude/backend_api_map.md:91`](../../.claude/backend_api_map.md#L91) and [`.claude/backend_api_map.md:270-276` → `CreateTaskDto`](../../.claude/backend_api_map.md#L270-L276)).
4. **The TypeScript model layer has no `CreateTaskDto`.** [`task.model.ts`](../../KanbAI-Web/src/app/features/board/models/task.model.ts) defines only `TaskResponseDto`, `MoveTaskDto`, and `TaskMoveResponse`. There is no client-side interface for the task-create request body, no envelope type for the create response, and no error-mapping branch for a `'create'` task operation (only `'move'` is covered by `mapTaskMoveErrorToUserMessage`).
5. **`BoardStateService` has no HTTP-driven task-create entry point.** Compare with [`BoardStateService.applyCreatedColumn`](../../KanbAI-Web/src/app/features/board/state/board-state.service.ts#L301-L312) (shipped with [#77](https://github.com/Gulybi/KanbAI-Web/issues/77)), which accepts a server-returned `ColumnResponseDto` and delegates to the shared append-if-new helper so the HTTP-success path and the SignalR echo path agree on dedupe. No equivalent method exists for tasks. The only entry points are the SignalR handler ([`onTaskCreated` at line 215](../../KanbAI-Web/src/app/features/board/state/board-state.service.ts#L215)) and the optimistic-move plumbing; an in-app create-task flow will need either a dedicated `applyCreatedTask` (HTTP path) or a deliberate decision to rely purely on the SignalR echo — a tech-spec decision.
6. **No event wiring between column and page for task creation.** Compare with the existing `taskDropped` / `taskOpened` outputs on [`BoardColumnComponent`](../../KanbAI-Web/src/app/features/board/components/board-column/board-column.component.ts) that re-emit CDK / card events up to the smart `BoardPageComponent`. A `taskCreated` (or equivalent) output and a matching parent handler do not exist.
7. **The input surface for typing a task name does not exist at all on the board.** The only existing text-input surface for task data is the task-detail drawer, which is focused on attachments and read-only task display ([`task-detail-panel.component.ts`](../../KanbAI-Web/src/app/features/board/components/task-detail-panel/task-detail-panel.component.ts)). There is no inline create form, no dialog, no column-scoped new-task input anywhere in the board feature area.

The user's lived experience today: "I just created my project, I see three empty columns that say 'Drop a task here'. There is nothing to drag. I cannot find any way to make a task. The app appears broken."

## Current State vs Desired State

### Current State
- **Each column renders a static empty-zone with no CTA.** [`board-column.component.html:23-26`](../../KanbAI-Web/src/app/features/board/components/board-column/board-column.component.html#L23-L26) shows only the `"Drop a task here."` paragraph when `tasks().length === 0`. There is no button, no icon, no toolbar, no keyboard hint.
- **Each column's header renders name + count and nothing else.** [`board-column.component.html:2-5`](../../KanbAI-Web/src/app/features/board/components/board-column/board-column.component.html#L2-L5) renders `<h2>column.name</h2>` and `<span>tasks().length</span>` — no trailing action slot, no `+` button, no overflow menu.
- **`BoardColumnComponent` has no task-create output.** [`board-column.component.ts`](../../KanbAI-Web/src/app/features/board/components/board-column/board-column.component.ts) defines `taskDropped` (CDK drop re-emit) and `taskOpened` (task-card activation re-emit) but no `taskCreateRequested` / `taskCreated` output. It is a pure presentational shell with no knowledge of task authoring.
- **`BoardPageComponent` has no add-task handlers.** [`board-page.component.ts`](../../KanbAI-Web/src/app/features/board/board-page/board-page.component.ts) has `handleTaskDropped`, `handleTaskOpened`, `handleTaskDetailClosed`, `handleAttachmentSelected`, plus the [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) add-column handlers (`openAddColumnFlow`, `handleAddColumnSubmit`, `handleAddColumnCancel`) — but no `openAddTaskFlow`, no `handleAddTaskSubmit`, no `handleAddTaskCancel`.
- **No per-column "add-task form" component exists.** Compare with [`BoardAddColumnComponent`](../../KanbAI-Web/src/app/features/board/components/board-add-column/board-add-column.component.ts) shipped by [#77](https://github.com/Gulybi/KanbAI-Web/issues/77): a presentational inline form with its own `FormControl<string>`, `required` / `maxLength(100)` / `whitespaceOnly` / `duplicateExisting` validators, `submitted(trimmedName)` / `cancelled` outputs, and keyboard handling for Enter/Escape. Nothing analogous exists for tasks.
- **`TasksApiService.createTask` does not exist.** The service has `moveTask` and the move-specific error-mapping helper only; no `POST /api/task/column/{columnId}` caller, no `'create'` operation branch.
- **`CreateTaskDto` and `TaskCreateResponse` are not defined in TS.** [`task.model.ts`](../../KanbAI-Web/src/app/features/board/models/task.model.ts) has `TaskResponseDto`, `MoveTaskDto`, `TaskMoveResponse` only.
- **`BoardStateService.applyCreatedTask` does not exist.** The only task-level append path is the SignalR handler `onTaskCreated`. The optimistic-move plumbing (`applyOptimisticTaskMove`, `rollbackOptimisticTaskMove`, `reconcileServerTaskMove`) is task-related but specific to moves, not creates.
- **No test coverage for a create-task path.** [`tasks-api.service.spec.ts`](../../KanbAI-Web/src/app/features/board/services/tasks-api.service.spec.ts) covers `moveTask` only. No component specs cover an add-task flow. No BoardStateService spec covers an HTTP-driven task-create reconciliation.
- **SignalR `TaskCreated` subscription is wired but only triggered by external events.** [`BoardStateService` effect at lines 62-97](../../KanbAI-Web/src/app/features/board/state/board-state.service.ts#L62-L97) subscribes `onTaskCreated` to `REALTIME_EVENT.TaskCreated`; the handler at [lines 215-242](../../KanbAI-Web/src/app/features/board/state/board-state.service.ts#L215-L242) is idempotent with dedupe-by-id and column-guard. It will correctly reconcile the client's own creates the moment [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) lands, without any state-service changes.
- **Behavior today (reproduction from the issue body):**
  1. User signs in, creates a new project with the [#70](https://github.com/Gulybi/KanbAI-Web/issues/70) flow (three default columns).
  2. The dashboard shows the new project card; user clicks it → `BoardPageComponent` loads at `/board/:projectId`.
  3. Board renders three columns: "To Do", "In Progress", "Done". Each shows the header (name + `0` count) and the `"Drop a task here."` hint. The trailing "+ Add column" button from [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) is visible at the end of the strip.
  4. User tries to create a task. There is no button anywhere on any column, no keyboard shortcut, no menu. Nothing happens.
  5. User is stuck. The only recoverable action is leaving the page. No task will ever be created through the UI in the current codebase.

### Desired State
- **Every column exposes a persistent "Add task" affordance.** When the board is populated (`columns().length > 0`), every column rendered by `BoardColumnComponent` exposes an "Add task" affordance — either in the column header, as a persistent footer slot below the task list, or inside the empty-zone when the list is empty (exact placement is a design-spec decision). The affordance is visible, keyboard-focusable, has an accessible name, and activates on click / Enter / Space.
- **Empty columns replace or supplement the dead-end hint with a CTA.** When `tasks().length === 0`, the empty-zone continues to communicate "this is a drop target" for drag-and-drop users AND presents a primary "Add task" action (for example: "Drop a task here." adjacent to an "Add your first task" button, or the empty hint is replaced entirely by an "Add task" CTA — design-spec decision). The hint alone is not sufficient; empty columns MUST have a clickable path to add a task.
- **Populated columns expose the affordance alongside the task list.** When `tasks().length > 0`, the affordance is still reachable (e.g. as a footer button below the last task, or a header control) without requiring the user to clear the column first. Its Tab order integrates cleanly with the existing task cards.
- **Activating the affordance opens an inline input surface scoped to that column.** The user types a task title; Enter submits, Escape cancels. The input has an associated `<label>` or `aria-label`, receives focus automatically on open, shows validation errors inline, and blocks submit while invalid — mirroring the [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) `BoardAddColumnComponent` pattern. Whether the surface is an inline input, a popover, or a modal dialog is a **design-spec decision**; what this doc requires is a per-column, keyboard-first authoring surface with parity to the column-create pattern.
- **Submit creates the task via the backend and it appears in the correct column.** On successful submit, the new task card is appended to that column's list (`taskOrder` greater than any existing task) and the task-count badge in the column header increments. Whether the insert is optimistic (local insert immediately, server reconcile on response) OR waits for the HTTP 201 before rendering is a **tech-spec decision** — the context requires only that (a) the user does not perceive a UI freeze, (b) double-submit never produces two tasks, and (c) the final state is identical to a fresh page load.
- **Focus moves to the newly created task and the creation is announced.** After success, keyboard focus lands on a predictable destination — the new task card, the same column's "Add task" affordance (so the user can rapid-add), or the input cleared for another entry. Focus MUST NOT fall to `<body>`. An `aria-live="polite"` announcement (re-using the existing `dragAnnouncement` region at [`board-page.component.html:32-38`](../../KanbAI-Web/src/app/features/board/board-page/board-page.component.html#L32-L38) OR a new region — tech-spec decision) informs screen-reader users of the addition.
- **Validation: non-empty, trimmed, ≤200 chars.** The title field enforces `required`, whitespace-only rejection, and `maxLength(200)` (matching the backend `CreateTaskDto.title` constraint at [`.claude/backend_api_map.md:274`](../../.claude/backend_api_map.md#L274)). The ≤100 constraint used for column names does NOT apply — tasks have their own backend-defined upper bound. Validation errors are announced via `aria-invalid` + inline error text and block submit until resolved.
- **Network / server failure surfaces a user-readable error and rolls back any optimistic insert.** On HTTP error of any kind (network 0, 4xx, 5xx, envelope `success: false`), the input surface stays open with the typed value preserved and an inline error message is shown. The error copy MUST come from a `mapTaskErrorToUserMessage` (or extension of the existing helper) that mirrors the `mapColumnErrorToUserMessage` envelope pattern — no status codes, URLs, stack traces leak to the UI. The error copy SHOULD be consistent in tone with the existing `moveError` pattern on the board page. If the insert was optimistic, the task is removed from local state before the error is surfaced so the final state matches the backend.
- **The task is keyboard-focusable and operable after creation.** The newly-created task card has all the affordances of any other task card: keyboard-focusable, openable into the detail drawer, draggable (via CDK pointer drag; keyboard drag is a separate future concern if not already shipped). It participates in the existing `TaskMoved` and `TaskCreated` SignalR reconciliation without any special-case handling.
- **Fully keyboard-accessible end to end.** Every step — opening the input, typing the title, submitting, cancelling, dismissing an error, focusing the new task — works with keyboard alone. The issue body explicitly calls this out: "Works without requiring drag-and-drop — fully keyboard-accessible."
- **Expected user flows:**
  1. **First-task empty-column path.** User opens a newly-created project with three empty columns → every column shows its name + `0` count + an "Add task" CTA alongside (or in place of) the `"Drop a task here."` hint. User clicks "Add task" on the first column → an inline input appears inside that column, focused, with an empty title field. User types "Wire up onboarding flow", presses Enter → the task appears at the top of the "To Do" column, the count flips to `1`, the empty-zone is replaced by the task card, the input surface closes (or clears for another — design-spec decision), focus lands on either the new card or the "Add task" affordance.
  2. **Populated-column append path.** User has a column with three existing tasks. User activates "Add task" on that column → the input appears below the last task (or in a column-specific slot — design-spec decision), focused. User types "Draft API spec", presses Enter → the new task appears at the end of the list (`taskOrder` greater than any existing task), count increments to `4`, the input closes or clears.
  3. **Validation — empty title path.** User activates the add-task flow, leaves the title empty, presses Enter → inline error ("Task title is required" or equivalent), input stays open, no API call is made, submit remains disabled.
  4. **Validation — whitespace-only path.** User types spaces only → treated as empty/invalid, same behaviour as (3).
  5. **Validation — too-long path.** User types a title longer than 200 characters → inline error ("Task title must be at most 200 characters" or equivalent), submit is disabled, no API call.
  6. **Cancel path.** User activates the flow, types something, presses Escape or clicks a Cancel affordance → the input closes with no API call, no state change, focus returns to the "Add task" trigger in the same column.
  7. **Network error path.** User submits a valid title; the request fails (network / 5xx). The input stays open with the typed value preserved. An inline error appears below the input ("We couldn't add this task. Please try again." or equivalent via the mapping helper). Submit is re-enabled so the user can retry. Any optimistic insert has been rolled back before the error surfaces, consistent with the existing `moveError` pattern.
  8. **401 during create.** The existing global `authInterceptor` handles redirect to login. The board page does not need task-scope handling. The add-task flow does NOT crash if it is unmounted mid-request during a redirect.
  9. **Persistence path.** After a successful create, refreshing the board (`F5`) shows the task in the column and position it was created in. The server is the source of truth for `taskOrder`; client-side optimistic ordering is reconciled against the response.
  10. **Rapid-add path.** User adds three tasks back-to-back to the same column, each with a unique title → all three appear in the order they were submitted; none are lost; no duplicate POSTs are issued (double-Enter / double-click MUST be idempotent); submit is never stuck.
  11. **Concurrent SignalR echo from the same user.** The user submits, receives the HTTP 201, and — moments later — the SignalR `TaskCreated` echo for the same task arrives. The existing dedupe-by-id in [`BoardStateService.onTaskCreated`](../../KanbAI-Web/src/app/features/board/state/board-state.service.ts#L215-L242) guarantees the task is not double-inserted. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) MUST NOT introduce any divergent append path that bypasses this dedupe.
  12. **Concurrent SignalR echo from another user / another tab.** Another user creates a task in the same column on the same board. The current user's `BoardStateService.onTaskCreated` handler appends the task within a single render cycle, the count in the column header increments, and the task is visible — no action required by the current user. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) MUST NOT regress this.
  13. **Create-then-immediately-drag path.** User creates a task in "To Do", then immediately drags it to "In Progress". The existing [#47](https://github.com/Gulybi/KanbAI-Web/issues/47) drag-and-drop + optimistic-move path works on the new task with no special handling — the card is a `BoardTask` like any other.
  14. **Create-then-open-detail path.** User creates a task, then clicks its card. The existing [#49](https://github.com/Gulybi/KanbAI-Web/issues/49) task-detail drawer opens with the new task's data, exactly as it would for a pre-existing task.

- **[#78](https://github.com/Gulybi/KanbAI-Web/issues/78) is soft-gated behind [#77](https://github.com/Gulybi/KanbAI-Web/issues/77)** in the sense that on an empty-column board ([#77](https://github.com/Gulybi/KanbAI-Web/issues/77)'s target state), [#78](https://github.com/Gulybi/KanbAI-Web/issues/78)'s per-column affordance has nowhere to attach. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) MUST NOT render any task-create affordance on a zero-column board — [#77](https://github.com/Gulybi/KanbAI-Web/issues/77)'s empty-state panel is the entirety of the zero-column UX.
- **[#78](https://github.com/Gulybi/KanbAI-Web/issues/78) inherits [#77](https://github.com/Gulybi/KanbAI-Web/issues/77)'s architectural patterns** for its inline-create component:
  - Presentational child component (`BoardAddColumnComponent` → task equivalent) with its own `FormControl<string>`, input-bound collaborator signals, `submitted(trimmedValue)` + `cancelled` outputs, and Enter/Escape handling.
  - Smart-parent orchestration: the HTTP call, the submitting flag, the server-error signal, and the close behaviour live in the smart parent (`BoardPageComponent` or `BoardColumnComponent` — tech-spec decision), not in the presentational child.
  - Server-error helper: a task-scoped analogue of `mapColumnErrorToUserMessage(err, 'create')` — tech-spec decides whether to extend the existing `mapTaskMoveErrorToUserMessage` with a `'create'` branch, introduce a sibling `mapTaskCreateErrorToUserMessage`, or generalise to `mapTaskErrorToUserMessage(err, operation)`.
  - SignalR dedupe: the client's own create + the SignalR echo of that same create MUST NOT double-insert. The state-service already guarantees this for the echo path — [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) only needs to not bypass it.
  - Smart-parent state-service entry point: whether [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) introduces a `BoardStateService.applyCreatedTask(projectId, columnId, TaskResponseDto)` analogue to [`applyCreatedColumn`](../../KanbAI-Web/src/app/features/board/state/board-state.service.ts#L301-L312), OR relies purely on the SignalR echo + HTTP-success-without-local-append, is a **tech-spec decision**. Both patterns are compatible with the existing state service.

### Related Work / Open Assumptions
- **Backend is already complete.** `POST /api/task/column/{columnId}` is live and documented ([`.claude/backend_api_map.md:91`](../../.claude/backend_api_map.md#L91) with `CreateTaskDto` at [`.claude/backend_api_map.md:270-276`](../../.claude/backend_api_map.md#L270-L276) — `title` required max 200, `content` optional, `assignedId` optional GUID). **No backend changes are required or permitted by [#78](https://github.com/Gulybi/KanbAI-Web/issues/78).**
- **`TasksApiService.createTask` is the first client method to call this endpoint.** Unlike the column path ([#77](https://github.com/Gulybi/KanbAI-Web/issues/77) could reuse `ColumnsApiService.createColumn` from [#70](https://github.com/Gulybi/KanbAI-Web/issues/70)), the task path has never been exercised by the client. The staff-engineer phase will define the method signature, DTO mapping, envelope-unwrap pattern (mirroring `ColumnsApiService.createColumn`), and error-mapping extension.
- **Minimal field set: title only.** The issue body explicitly specifies a "quick-create flow, name-only" as the preferred approach; a richer "task-creation dialog/panel (description, assignee, etc.)" is mentioned as an alternative but the **context doc requires only that title is captured**. `content` and `assignedId` are out of scope — both are optional on the backend and the client will omit them on create (the backend accepts `null`/undefined for both per [`.claude/backend_api_map.md:275-276`](../../.claude/backend_api_map.md#L275-L276)). Whether the tech/design spec chooses a richer flow is a **deliberate decision, justifiable in the spec** per the issue body: "An inline text input appended to the column list (quick-create flow, name-only), or / A task-creation dialog/panel (richer flow with description, assignee, etc.)" — pick one, justify in tech spec.
- **`CreateTaskDto.title` max is 200 chars**, not the 100 used for columns. The tech spec MUST NOT inadvertently apply the column `maxLength(100)` constraint to tasks.
- **`taskOrder` is not in `CreateTaskDto`.** The backend assigns it server-side (mirroring the column pattern where the client may optionally pass `columnOrder`). The client MUST NOT send `taskOrder` in the create request and MUST accept the server's returned `taskOrder` as authoritative — this is important because the existing [`BoardStateService.onTaskCreated`](../../KanbAI-Web/src/app/features/board/state/board-state.service.ts#L215-L242) sorts by `taskOrder` ascending.
- **Duplicate task titles within a column are ALLOWED.** Unlike columns where [#70](https://github.com/Gulybi/KanbAI-Web/issues/70) / [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) apply a case-insensitive-trimmed duplicate validator (because two same-named columns are visually indistinguishable), tasks legitimately repeat across a column (e.g. "Follow up with client" three times for three different clients). [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) MUST NOT apply a duplicate-title guardrail on create.
- **Optimistic insert vs. wait-for-response is a tech-spec decision.** The existing code base does both: [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) waits for the HTTP 201 before appending via `applyCreatedColumn`; [#47](https://github.com/Gulybi/KanbAI-Web/issues/47) inserts optimistically and reconciles on response. Either pattern is compatible with [#78](https://github.com/Gulybi/KanbAI-Web/issues/78). What this doc requires: (a) no double-insert, (b) no visual UI freeze, (c) on error, the final state matches the server (no phantom tasks left behind), (d) SignalR echo dedupe continues to work regardless of chosen pattern.
- **Transient "Adding…" state is required.** While the HTTP create is in flight, the submit affordance is disabled and the user has some signal the system is working (a spinner, a "Adding…" label, a disabled input — design-spec decision). Rapid double-click / double-Enter MUST NOT produce two POSTs.
- **Error-mapping helper extension.** `mapTaskMoveErrorToUserMessage` is move-only. The tech spec will decide whether to extend it with a `'create'` operation parameter (mirroring `mapColumnErrorToUserMessage(err, operation)` from [#70](https://github.com/Gulybi/KanbAI-Web/issues/70)), introduce a sibling helper, or inline a create-specific mapper. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) requires only that the UI receives user-readable copy that never exposes HTTP status codes, URLs, stack traces, or backend envelope `errors[]` contents.
- **No new dependencies.** Angular Reactive Forms (already present), Angular CDK (already present), the existing `FormInputComponent` (used by [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) — preferred per precedent), the existing `whitespaceOnlyValidator` from [#70](https://github.com/Gulybi/KanbAI-Web/issues/70). No new npm packages.
- **Test coverage is a hard requirement.** Unit tests for the new API method, the new state-service entry point (if introduced), the new component, the column-level wiring, the page-level wiring, validation paths, error paths, focus-management, SignalR echo dedupe. See Acceptance Criteria § Verification for specifics.
- **Mobile / responsive behavior.** The per-column "Add task" affordance must remain reachable on small viewports where the column strip may be horizontally scrolled (matching [#77](https://github.com/Gulybi/KanbAI-Web/issues/77)'s mandate for the trailing "+ Add column"). The inline input surface must remain visible without horizontal scroll on viewports <640px. Specific responsive spec is delivered by the web-designer phase.

## Acceptance Criteria

### Per-column "Add task" affordance (populated board)
- [ ] When the board has ≥1 column and a user is viewing it, every column rendered by `BoardColumnComponent` exposes an "Add task" affordance. The affordance is visible to sighted users, keyboard-focusable via Tab, activatable on Enter and Space, and has an accessible name that is not icon-only (e.g. visible "Add task" text or `aria-label="Add task to <column name>"`). Exact placement (header trailing icon, footer slot below task list, inside empty-zone, etc.) is a design-spec decision.
- [ ] When a column is empty (`tasks().length === 0`), the empty-zone either (a) supplements the existing `"Drop a task here."` hint with a primary "Add task" CTA or (b) replaces the hint entirely with an "Add task" CTA. The empty-zone MUST NOT remain a dead-end with only the drop-hint — the issue body explicitly requires "Empty column state shows both 'Drop a task here' and a primary 'Add task' action — empty ≠ dead end." Whether both are shown or only the CTA is a design-spec decision, but a CTA MUST be present.
- [ ] When a column has ≥1 task (`tasks().length > 0`), the "Add task" affordance remains reachable — it is not hidden behind a task-list scroll, not gated behind a menu that requires extra activation, and is positioned predictably (e.g. as a footer slot below the last task, or in the column header — design-spec decision).
- [ ] The Tab order within a column is logical: column header controls (if any) → each task card → "Add task" affordance → (next column). Changing this order is not required by [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) if the design-spec places the affordance elsewhere, but the final Tab order MUST be predictable and documented in the design spec.

### No affordance on zero-column boards
- [ ] When `columns().length === 0`, NO "Add task" affordance is rendered anywhere on the page. The zero-column board UX is entirely owned by [#77](https://github.com/Gulybi/KanbAI-Web/issues/77)'s empty-state panel (the empty-state CTA is "Add column", not "Add task"). Rendering a task-create affordance in a state where no column exists is a bug.

### Add-task input flow
- [ ] Activating the "Add task" affordance (click, Enter, Space) opens an input surface scoped to that column where the user can type a task title. Whether this is inline (within the column), a popover, or a modal is a design-spec decision.
- [ ] The input has an associated `<label>` or `aria-label` so assistive tech announces its purpose (e.g. "Task title" or "New task title for <column name>").
- [ ] The input accepts Enter to submit and Escape to cancel.
- [ ] The input surface has an explicit submit affordance (button labelled e.g. "Add", "Create", or "Add task") and an explicit cancel affordance (button or ✕). Enter / Escape shortcuts are additive, not a replacement.
- [ ] On open, keyboard focus lands inside the title input automatically within a single render cycle (the user can start typing without extra interaction).
- [ ] The input surface displays validation errors inline (timing is a design-spec decision: on input, on blur, or on submit-attempt).
- [ ] Opening the add-task surface on one column does NOT automatically close or clear the add-task surface on another column (if multiple columns allow concurrent open — design-spec decision; either mutually-exclusive-one-at-a-time OR concurrent-per-column is acceptable, so long as the behaviour is consistent and documented).

### Validation rules
- [ ] An empty title (zero characters or whitespace-only after trimming) blocks submit and shows a required-field error inline.
- [ ] A title longer than 200 characters blocks submit and shows a "Task title must be at most 200 characters" (or equivalent) error inline. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) MUST NOT reuse the 100-char constraint used for columns.
- [ ] While any validation error is active, the submit affordance is disabled (not merely ignored on click) and `aria-invalid="true"` is set on the input so screen readers announce the invalid state.
- [ ] Validation errors clear within a single render cycle once the user's edit resolves them.
- [ ] Duplicate task titles within a column are ACCEPTED (no client-side duplicate-title validator applies, unlike columns). Two tasks named "Follow up with client" in the same column is a supported state.

### Submission success
- [ ] A valid submit calls `TasksApiService.createTask(columnId, { title: <trimmed> })` (exact method name / signature is a tech-spec decision) exactly once per submission. Rapid double-submit (double-click, double-Enter) MUST NOT produce two POSTs.
- [ ] The POST body contains exactly `{ title: <trimmed title> }`. `content` and `assignedId` are NOT sent by [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) (they are out of scope per the issue body's "quick-create flow, name-only"). `taskOrder` is NOT sent by the client — the backend assigns it.
- [ ] While the submission is in flight, the submit affordance is disabled and the input surface shows a pending / "Adding…" state so the user understands the system is working. The affordance is re-enabled on success (after close/clear) or on error (so the user can retry).
- [ ] On HTTP 201 success, the new task is visible in the target column with the title the user typed, at the end of that column's task list (`taskOrder` greater than any existing task in that column — the server's returned `taskOrder` is authoritative).
- [ ] On success, the column's task-count badge (rendered at [`board-column.component.html:4`](../../KanbAI-Web/src/app/features/board/components/board-column/board-column.component.html#L4)) reflects the new count within a single render cycle.
- [ ] On success, the input surface closes OR clears to accept another task (design-spec decision; both are acceptable as long as the behaviour is consistent, documented, and the user is never stranded in a half-open state).
- [ ] On success, keyboard focus moves to a predictable destination — the new task card, the same column's "Add task" affordance, or the now-cleared input surface (tech/design-spec decision) — and MUST NOT fall to `<body>`.
- [ ] On success, an `aria-live="polite"` announcement informs screen-reader users of the addition (e.g. "Task '<title>' added to <column name>" or equivalent). The existing `dragAnnouncement` region at [`board-page.component.html:32-38`](../../KanbAI-Web/src/app/features/board/board-page/board-page.component.html#L32-L38) MAY be reused, or a dedicated region introduced — tech-spec decision.
- [ ] After a successful create, refreshing the page (`F5`) shows the new task in the same column and the same position it was displayed post-create.

### Submission error handling
- [ ] On HTTP error of any kind (network/0, 4xx, 5xx, envelope `success: false`), the input surface stays open with the user's typed value preserved and a user-readable error sentence shown inline.
- [ ] Error copy MUST NOT expose HTTP status codes, URLs, stack traces, or backend envelope `errors[]` contents to the UI.
- [ ] Error copy is consistent in tone with the existing `moveError` pattern on the board page (e.g. "We couldn't add this task. Please try again." for the generic case; "We couldn't reach the server. Please check your connection and try again." for network/0). A task-scoped mapping helper (extension of `mapTaskMoveErrorToUserMessage` or a sibling) is introduced by the tech spec.
- [ ] On error, the submit affordance is re-enabled after the failure is surfaced so the user can correct and retry without re-opening the surface.
- [ ] On HTTP 401, the existing global `authInterceptor` handles redirect. The board page / column / create component MUST NOT crash or leak subscriptions if the surface is unmounted mid-request during a redirect.
- [ ] On HTTP 404 (column gone or project gone), the error copy indicates the column/project no longer exists. The page does not need to navigate automatically — the user sees the error and can choose to leave.
- [ ] On HTTP 403 (caller no longer a project member), the error copy surfaces a meaningful sentence ("You are no longer a member of this project" or equivalent from the mapping helper); no silent failure.
- [ ] If the implementation chose optimistic insert, on any HTTP error the optimistic task is removed from local state BEFORE the error is surfaced — the final rendered state matches the server (no phantom task card remains).

### SignalR echo idempotence (no regressions to [#46](https://github.com/Gulybi/KanbAI-Web/issues/46))
- [ ] When the client's own create succeeds and the SignalR `TaskCreated` event for the same task arrives shortly after, the task MUST NOT be double-inserted into local state. The existing dedupe-by-id in [`BoardStateService.onTaskCreated`](../../KanbAI-Web/src/app/features/board/state/board-state.service.ts#L215-L242) guarantees this at the state-service level — [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) MUST NOT bypass or duplicate that reconciliation.
- [ ] When another user (or the current user from a second tab) creates a task in the same column, the `TaskCreated` event fires and the new task appears in the current user's column within a single render cycle, without any action by the current user. The task-count badge increments. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) MUST NOT regress this existing behaviour.

### Cancel & dismissal
- [ ] Activating Cancel (explicit button, Escape key, or dismissal if the surface is a modal/popover) closes the input surface WITHOUT issuing any API call and WITHOUT changing board state.
- [ ] On cancel, keyboard focus returns to the "Add task" affordance that opened the surface.
- [ ] Re-opening the add-task surface after a cancel shows an empty field (no leftover typed text from the cancelled attempt).

### Accessibility
- [ ] All new interactive controls (per-column "Add task" affordance, input, submit button, cancel button) have accessible names, are keyboard-focusable, and operable with Enter and Space (buttons) / Enter and Escape (input).
- [ ] The whole create-task flow is operable without drag-and-drop (issue body: "Works without requiring drag-and-drop — fully keyboard-accessible").
- [ ] Validation errors are announced to assistive tech via `aria-invalid` on the field + `aria-describedby` (or equivalent `aria-live` region) that references the error message.
- [ ] Successful task creation is announced to assistive tech via `aria-live="polite"` within a single render cycle of the task appearing.
- [ ] The newly-created task card is focus-reachable immediately after creation — it is not hidden by a transition that traps focus, not delayed by an animation that outlasts the announcement.
- [ ] The board page, in a state with ≥1 column and at least one open add-task surface, passes `axe-core` with zero critical or serious violations.
- [ ] Color contrast on all new text, button backgrounds, placeholders, and error text meets WCAG AA (4.5:1 body text, 3:1 large text and non-text controls).

### Styling & Consistency
- [ ] The per-column "Add task" affordance and the inline input surface visually integrate with the existing `BoardColumnComponent` styling (typography scale, spacing, button styles, color tokens). Exact visual spec is delivered by the web-designer phase.
- [ ] The input surface uses [`FormInputComponent`](../../KanbAI-Web/src/app/features/auth/components/form-input/form-input.component.ts) (mirroring [#77](https://github.com/Gulybi/KanbAI-Web/issues/77)'s `BoardAddColumnComponent` precedent) unless the tech spec proposes an alternative with justification.
- [ ] The design visually distinguishes an "open add-task surface" from a regular task card, so users do not confuse the in-progress input with an existing task row.
- [ ] Responsive: on viewports <640px, the per-column "Add task" affordance remains visible within the column's scroll window; the inline input surface does not introduce horizontal scroll on the column.

### Verification
- [ ] `npm run build` succeeds with no new errors or warnings attributable to this feature.
- [ ] `npm run test -- --watch=false` passes with no **INTRODUCED** test failures. Pre-existing failures are documented but not blocking per CLAUDE.md.
- [ ] New unit tests cover, at minimum:
  - `TasksApiService.createTask` (or equivalent) — envelope-unwrap on success, observable-error on `success: false`, observable-error on `data == null`.
  - Task-scoped error-mapping helper — one case per HTTP status branch (0, 401, 403, 404, 4xx generic, 5xx) and a fallthrough.
  - `BoardStateService.applyCreatedTask` (if introduced) — no-op on stale project, no-op on unknown column, no-op on already-known task id, append + sort on new-to-state task.
  - Per-column affordance renders when `columns().length > 0` AND the specific column is visible; does not render on zero-column boards.
  - Empty-zone empty-state supplements or replaces the drop-hint with a visible CTA; the hint-only empty-zone no longer appears for authenticated board users.
  - Activating the affordance opens the input surface, moves focus into it, and clears any prior server-error copy.
  - Submit invokes `TasksApiService.createTask` with the trimmed title and the correct column id.
  - Double-submit is prevented (one POST per logical submission regardless of click cadence).

  - Successful response updates local state such that the task appears in the correct column; task-count badge increments.
  - Error response keeps the input open with typed value preserved and user-readable copy displayed.
  - Cancel (Escape / cancel button) closes the surface, issues no POST, restores focus to the "Add task" affordance.
  - SignalR echo of the client's own just-created task does not double-insert (dedupe-by-id is exercised end-to-end).
  - Navigation-away-mid-request does not leave an orphaned subscription or a ghost task (takeUntilDestroyed path is exercised).

## Edge Cases & Explicit Out-of-Scope

### In-scope edge cases (must be handled)
- [ ] **User opens the add-task surface and immediately presses Escape before typing:** surface closes, no API call, focus returns to the "Add task" affordance.
- [ ] **User types a title and then the column is deleted by another user (SignalR `ColumnDeleted`):** the column disappears from the strip (existing [#46](https://github.com/Gulybi/KanbAI-Web/issues/46) behaviour); the open input surface in that column is unmounted along with it; no orphan state, no crash. If the user had pressed Enter just before the column deleted, the HTTP call returns 404 and the error handling above applies — but since the column is already gone from local state, the inline error has nowhere to render. A toast / global error surface is NOT required by [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) — graceful no-op (no crash, no stuck "Adding…" spinner) is sufficient.
- [ ] **User opens two columns' add-task surfaces at once (if design permits concurrent open):** each surface maintains independent typed values, independent validation state, independent pending / error state. Submitting one does not affect the other.
- [ ] **User types a title with leading/trailing whitespace:** trimmed before being sent to the backend (matches the backend's trim behaviour and the [#70](https://github.com/Gulybi/KanbAI-Web/issues/70) / [#77](https://github.com/Gulybi/KanbAI-Web/issues/77) convention).
- [ ] **Title at exactly 200 characters:** accepted (boundary is inclusive, matching backend `max 200`).
- [ ] **User navigates away from the board while the create-task request is in flight:** the subscription is cleaned up via `takeUntilDestroyed(this.destroyRef)` (mirroring the existing pattern in `BoardPageComponent`); no stale setState on unmounted component; on return to the board, the task appears if the server processed the create before the tab closed (via the initial columns/tasks GET — a future reload), OR does not appear if the server rolled back. Either outcome is acceptable; [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) is not responsible for solving non-transactional backend semantics.
- [ ] **Rapid opens and cancels** of the add-task surface do not leak subscriptions, event handlers, or scroll-lock state.
- [ ] **User submits, receives 5xx, corrects nothing, re-submits:** a second POST is issued; if that succeeds, the task appears. No stale "Adding…" state carries over from the first attempt.
- [ ] **User has the add-task surface open on column A, then drags a task from column A to column B:** the open surface does not close (the drag operates on an existing task card, not on the input surface) and the drag's own flow is unaffected. [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) MUST NOT interfere with [#47](https://github.com/Gulybi/KanbAI-Web/issues/47)'s drag-and-drop behaviour.
- [ ] **Two users creating tasks concurrently in the same column:** each user's own create may echo back via SignalR while the other user's create is also echoing. The dedupe-by-id at the state-service level guarantees no duplicate rows; the final sort-by-`taskOrder` guarantees a consistent order. The UI does not need to do anything special other than rely on existing `onTaskCreated`.
- [ ] **Board reconnect during an open add-task surface:** the user's typed value is preserved (component state); the SignalR connection reconnects via the existing `effect` in `BoardStateService`; submitting after reconnect behaves identically to submitting pre-disconnect.
- [ ] **"Add task" affordance clicked on a column that has just been SignalR-deleted between render and click:** the column is no longer in state; the click either lands on a stale DOM reference (unlikely under Angular's re-render) OR the column is gone and the click has no target. Either path is a graceful no-op; no crash, no ghost surface.

### Explicitly out of scope for [#78](https://github.com/Gulybi/KanbAI-Web/issues/78)
- **Task description / content field.** `CreateTaskDto.content` is optional on the backend; the client will omit it on create. Adding a description editor inside the add-task flow is a future ticket.
- **Assignee picker on create.** `CreateTaskDto.assignedId` is optional; the client will omit it. A member-picker UI for assigning on create is out of scope (requires listing project members, currently not surfaced inside the board).
- **Inserting a task at a specific position (not the end).** [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) only creates at end-of-column (max `taskOrder` + 1, or whatever the backend chooses). Mid-list insert is a future enhancement.
- **Task rename / edit on an existing board.** Out of scope; backend endpoint does not exist per [`.claude/backend_api_map.md:163`](../../.claude/backend_api_map.md#L163).
- **Task delete on an existing board.** Out of scope for the same reason.
- **Bulk task creation** (paste-a-list-of-lines behaviour). Out of scope — one task per submit.
- **AI-suggested task titles or auto-complete.** Out of scope despite the milestone theme; [#78](https://github.com/Gulybi/KanbAI-Web/issues/78) is a foundational UX ticket, not an AI feature.
- **Task templates / presets.** Out of scope.
- **Drag-to-create** (e.g. dragging a file onto the column to create a task). Out of scope; attachment UX is task-scoped (an existing task must already exist to receive an attachment), shipped by milestone #6.
- **Keyboard drag-to-reorder** the just-created task. Keyboard operation of the drag-and-drop flow is not part of [#78](https://github.com/Gulybi/KanbAI-Web/issues/78); the newly-created task is a normal `BoardTask` and inherits whatever keyboard-drag support [#47](https://github.com/Gulybi/KanbAI-Web/issues/47) ships (today: pointer-only).
